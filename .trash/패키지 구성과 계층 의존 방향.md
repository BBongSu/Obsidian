SQL 위치와 Java 연결

- 위치: SQL은 전부 src/main/resources/mapper/<기능>/XxxMapper.xml에 있어요. application.yml이 mybatis.mapper-locations: classpath:mapper/**/*.xml로 이 파일들을 읽어요.
- 연결 방식: XML의 namespace가 인터페이스 전체 경로와 같고, 각 쿼리 id가 메서드 이름과 같아요.
  - ProductMapper.xml: namespace="com.example.shop.product.mapper.ProductMapper"이고, <select id="selectProductOne">이 ProductMapper.selectProductOne(@Param("productCode"))에 연결돼요.
  - StockLotMapper.xml: selectNextLotSeq, insertLot, selectLotOne, selectInStockListByProduct, updateLotQtyAndStatus, updateLotStatus가 각각 같은 이름의 인터페이스 메서드에 연결돼요.
- 결과 매핑: resultMap(productMap, stockLotMap)으로 조회 결과를 domain record에 바로 매핑해요. 시퀀스 값은 resultType="long"으로 받아요.
- SQL 방언: MSSQL 문법이에요(WITH (NOLOCK)). 실제로는 H2를 MODE=MSSQLServer로 돌려요. 애플리케이션 DB는 실행할 때마다 새로 만드는 메모리 DB이고, 시작할 때 schema.sql, data.sql 순서로 초기화해요.
- 컨벤션: 사내 규칙 docs/conventions/mybatis-convention.md이 이 구조를 정해 둬요. C1은 SELECT마다 NOLOCK을 붙이라는 규칙이에요. C4는 namespace와 id를 인터페이스와 맞추고 @Param을 쓰라는 규칙이에요. C5는 select{대상}{One|List|Count} 같은 이름 규칙이에요.

확인된 사실과 추론 구분

확인된 사실 (파일에서 직접 봤어요)
- 위 표의 패키지, 어노테이션, import 관계, XML의 namespace와 id, mapper-locations 설정이에요.
- domain 패키지는 com.example 아래 다른 패키지를 하나도 import하지 않아요.
- 기능 사이 의존은 LotService가 ProductService를 부르는 것 하나뿐이에요. mapper를 직접 건너 쓰는 곳은 없어요.
- schema.sql에 stock
- 다른 기능의 데이터가 필요하면 그 기능의 Service를 통해 접근하는 것이 팀의 관례로 보여요. 근거는 사례 하나(LotService)뿐이에요.
- HoldReason enum과 stock_hold 테이블은 아직 판매 보류 API가 없는 상태에서 미리 만들어 둔 것으로 보여요. 4모듈 "신규 API 구현"과 관련 있어 보여요.
- 매퍼 인터페이스 안에 업무 규칙(로트 번호 형식, nextLotNo)이 들어 있는 건 계층 경계를 조금 넘는 설계예요. 의도한 것인지는 알 수 없어요.
